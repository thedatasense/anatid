# Does an agent answer better? The answer-quality benchmark

The Phase 0 benchmark ([`benchmarks.md`](benchmarks.md)) says how fast anatid stores and recalls
a million memories and whether the graph it returns is the right one. It says nothing about the
thing an agent developer wants to know, which is whether an agent gives better answers with
anatid in front of it than with the obvious alternatives: a Markdown file, a full-text index, a
vector index. This benchmark asks that question directly. Same model, same prompt, same 150
questions, same 1,200-token memory budget, eleven memory systems, and the losses published next
to the wins.

Everything here is produced by one command, `python -m bench.quality.run`, from the code under
`bench/quality/`. Every model call is cached on disk, so a rerun costs nothing and gives the same
numbers; `--offline` refuses the network to prove it. The numbers below are for two seeds of the
corpus generator, because one world turned out not to be enough to rank the systems.

## Limitations, first

1. **The corpus is synthetic and generated by us.** `bench/quality/gen_corpus.py` simulates a
   small engineering organisation over eighteen months and renders its events as short notes from
   a few dozen templates. The entities are few, the notes are short and clean, and the questions
   have exact gold answers by construction. Real notes are longer, messier and less consistent
   about names, and real questions are less well posed. Nothing here says how any system behaves
   on your notes.
2. **The judge is the same model as the answerer.** `z-ai/glm-5.3-flash` both answers and grades,
   and a judge that shares the answerer's blind spots can agree with a wrong answer. A lexical
   scorer is reported next to the judge, with their agreement rate, so the two can be checked
   against each other; they agree on 95% to 100% of answers per system.
3. **n is small.** 150 questions, 25 per category, over about 178 notes. One question in a
   category is 4% of that category. Differences of a few questions between systems are noise, and
   the two seeds below disagree about the order of the middle of the table.
4. **One seed is one world.** The generator writes a different organisation for every seed, with
   the same shape. We ran two. Where the two agree, the finding is probably about the systems;
   where they disagree, it is about the world, and both are shown.
5. **The budget is what makes the comparison a comparison.** The whole corpus is about 6,300 tokens
   with headers, so it fits in a prompt, and the unbudgeted Markdown variant that receives all of it
   is the upper bound of "just put everything in the prompt". That variant would not exist at ten
   times the corpus, and nothing here says how any system behaves there.
6. **Tokens are counted as four characters each.** The harness prefers `tiktoken`'s `cl100k_base`
   when the package is importable; it was not installed for these runs, so every system was cut at
   `ceil(chars / 4)` tokens, applied identically. `--counter chars4` pins that choice for a rerun,
   because a different counter is a different budget and a cold cache.
7. **The model is not deterministic across days.** The cache makes a rerun exact; a cold rerun
   against the provider on another day may answer some questions differently.
8. **The gold-extracted store (S5) is an oracle, not the product.** It shows what anatid's
   retrieval does when extraction is perfect. The product is S4, whose patches the model wrote.
9. **The anatid systems get more structure per line.** Each recalled memory is rendered with its
   validity interval, its writer and the versions it superseded; the baselines get the raw dated
   notes. Both carry the date and the source label, so both can answer temporal and provenance
   questions. What differs is how much history fits in the budget.
10. **The fused baselines are not tuned.** `hybrid` and `vector-prf` use the fusion constant anatid
    uses and one round of feedback over three notes. Someone tuning a retrieval stack for this
    corpus would do better than either, and probably better than anatid.
11. **Tie order is pinned in the harness.** anatid's BM25 arm returns equal scores in an order that
    varies between calls, because DuckDB sums the per-term contributions in parallel. The harness
    rounds arm scores to six decimals and breaks ties by memory id, for anatid's arms and for the
    BM25 and vector baselines alike, so a rerun asks the same prompts. Ranking is otherwise
    unchanged.

## Method

### The corpus

`bench/quality/world.py` simulates twelve services, eight people and five teams from 2025-01-06
to 2026-06-26. Services change owner one to three times, people move between teams, pagers rotate
every four to eight weeks, dependencies are rewired, deploy windows change, incidents get reviews
with root causes and decisions, and three handover notes name the wrong team and are corrected one
to four weeks later. `gen_corpus.py` renders the events as notes with a date and a source label
(`standup/<team>/<date>`, `handover/<date>-<service>`, `incident-review/<INC id>`), seven ways to
write a handover, three names for every service and team, and dates in the body written relatively
("as of today") so the header carries the absolute date. Every system receives the same string per
note, `[date] source: text`.

The questions are asked as of 2026-06-30, 25 per category:

| category | asks | example |
| --- | --- | --- |
| `single_fact` | a fact stated once and never changed | What was the root cause of INC-2026-003? |
| `knowledge_update` | the current value of something that changed | Which team owns search-indexer now? |
| `temporal` | the value at a date, the value before a change, or when a change happened | Which team owned billing-api on 2025-04-14? |
| `multi_hop` | two or three facts chained across notes that share no keyword | Who is on call for the team that owns the service webhooks depends on? |
| `provenance` | which note said it, and on what date | Which note recorded the handover of search-indexer to Atlas, and when? |
| `abstention` | plausible, and not answerable from the notes | Which service does the event-bus depend on? |

Each question carries its gold answer, accepted aliases (team and service forms, full names, date
formats), the notes that support it, and, for questions whose value changed, the distractors: values
that were once true and are now wrong. The corpus README (`bench/quality/README.md`) has the
counts by subtype. `gen_corpus --verify` ingests the gold patches into anatid and checks the graph
against the simulation, so the gold is right by construction.

### The prompt and the budget

Every system answers with one prompt template. The system message tells the model to answer only
from the memory provided, to reply exactly `I don't know` when the memory does not contain the
answer, to answer in one short line, to answer for the moment the question asks about (today is
2026-06-30), and to treat a later entry as superseding an earlier one on the same subject. The user
message is the memory block, then the question.

A system decides one thing: which lines go into the memory block. It returns its ranking, and one
function, `fit_budget`, keeps the longest prefix whose token count fits in 1,200 tokens. The cut is
identical for every system. The Markdown system hands over its file newest first and shows the kept
tail oldest first; every other system shows its lines in rank order.

Answering and judging use `z-ai/glm-5.3-flash` through OpenRouter at temperature 0. The model
reasons before it answers; an answer that came back empty because the reasoning used the whole
completion cap is asked once more with a cap three times larger, and one still empty is scored as
wrong. None was, in either run. Embeddings are `openai/text-embedding-3-small` at 1,536
dimensions through the same endpoint, shared by the vector baseline and the anatid systems so they
rank with identical vectors.

### The systems

| code | system | what goes into the prompt |
| --- | --- | --- |
| S1 | `markdown` | every note appended to one Markdown file in arrival order; the most recent notes that fit |
| S1, no budget | `markdown-full` | the whole file, no budget; the upper bound of the plain prompt at this corpus size |
| S2 | `bm25` | DuckDB `fts` over the raw notes, Best Match 25 (BM25) with Porter stemming, English stop words and digits kept; top notes first, newest first on ties |
| S3 | `vector` | `text-embedding-3-small` over the raw notes; top notes by cosine, newest first on ties |
| S2+S3 | `hybrid` | the BM25 and cosine rankings fused with Reciprocal Rank Fusion (RRF, k = 60), ties by cosine rank |
| S3, PRF | `vector-prf` | the vector ranking, then the question with the top three notes appended and ranked again, the two fused with RRF; one round of pseudo-relevance feedback (PRF) |
| S4 | `anatid` | notes ingested through `anatid.ingest` with the same chat model as extractor and the same embedder on the handle; `recall` with every arm; each memory rendered with its validity interval, its writer and the versions it superseded |
| S4t, S4v, S4g | `anatid-text`, `anatid-vector`, `anatid-graph` | the S4 store read through one arm at a time |
| S5, oracle | `anatid-gold` | the same pipeline fed the corpus's gold patches through `ScriptedExtractor`; perfect extraction, so the S4 to S5 gap is what the model's extraction costs |

`hybrid` and `vector-prf` exist because anatid fuses three arms and runs a graph expansion. A
comparison against single-arm baselines alone could not say whether the fusion, the second round
or the memory made the difference. anatid's arms and its fusion are called through the harness
(`fused_recall`) so that tie order is pinned; the ranking is anatid's.

Ingestion is the same for S4 and S5: one call to the pipeline per note, in arrival order, with
`now` the note's date and `writer` and `source` its label, so the memories carry a validity interval
and a writer that answer provenance questions the way a header does for the others. Memory ids are
allocated by a counter so the extractor's prompt, which lists existing memories by id, is the same
on every run.

### Scoring

Two scorers, both blind to the system. The **LLM judge** sees the question, the gold, the aliases,
the category's grading rule and the answer, at temperature 0, and returns one JSON verdict; it is
never told where the answer came from, and the test suite checks that the system name does not
reach it. The **lexical scorer** is a normalised whole-word match of the gold or an alias, with a
stale value (a distractor) named before the gold counted wrong, and a refusal counted right only for
abstention questions. Their agreement rate is reported per system.

Three measures that accuracy alone hides: **abstention precision**, the share of refusals that
were right to refuse; **false refusals**, refusals on questions the notes do answer; and **stale
answers**, answers to knowledge-update or temporal questions that name a value that was once true.

### Caching, cost and reproducibility

Every model call goes through one client that caches the response on disk keyed by a SHA-256 of
the request and records the network latency and the provider's reported cost with it. A replay
reports the recorded latency and cost and charges nothing. The key is read from `OPEN_ROUTER_KEY`
or `.env` and is not part of any cache key, cache file or result file. Every prompt, every retrieved
context and every answer is saved under `bench/quality/results/<run>/<system>/`, and the report is
rendered from `summary.json` with nothing typed in by hand.

The categories separate the systems more than the totals do. Single facts, current values, dates
and provenance are solved by every raw-note retriever in both worlds (92% to 100%): one note holds
the answer, and BM25 or cosine finds that note. anatid is a few questions behind on each of those
on the committed corpus (92%, 88%, 80%, 92%) and closer on seed 7 (96%, 96%, 100%, 96%). The
misses are facts the extractor did not write down or attached to the wrong entity; the stale
answers are handovers and rotations whose old edge was never closed.

Multi-hop is where the systems are told apart, and it is also where n is smallest: 25 questions,
so one question is four points. anatid answers 10 of 25 on the committed corpus, behind vectors
at 13 and vectors with feedback at 15, and 15 of 25 on seed 7, ahead of vectors and vectors with
feedback at 14 and the fusion at 12. Its vector arm alone does better in both worlds, 14 and 17.
The oracle answers 19 and 21, so the chain is in the graph when the graph is right. The
model-built graph opened about as many edges as the gold (86 and 87 against 95 and 99) but closed
under half as many (29 and 25 against 61 and 65), so a service that changed owner tends to keep
its old owner as a second edge, and a chain through it lands on a stale team. The whole file answers
22 and 24 of 25, which says the model can chain the facts when all of them are in front of it.

The lexical scorer's tables are in each run's `REPORT.md`. It agrees with the judge on 95% to
100% of answers per system; the systems it disagrees with most are the anatid ones, whose answers
are more often a paraphrase or a longer list than the gold string, which the judge accepts and a
whole-word match does not.

### Knowing when to stop

The instruction to say `I don't know` works: every system refused every abstention question in
both worlds, with one exception (vectors with feedback answered one on the committed corpus, naming
a previous owner the notes never recorded), so abstention recall is 96% to 100% across the board.
The difference is on the other side. The budgeted Markdown file refuses most answerable questions
because the answer is rarely among the most recent 35 notes (68% and 61% false refusals). The
raw-note retrievers refuse 2% to 4% of answerable questions. anatid refuses 14% and 9% of them,
and its text arm alone more, because a fact the extractor did not write down, or wrote down
attached to the wrong entity, is a fact recall cannot find. The graph arm alone refuses almost
everything: it returns only memories about the entities the question names, and for the 64 and 70
questions where the automatic seeding matched no entity it returns nothing at all.

The vector arm carries the system. Alone it beats the fused recall by seven points on the
committed corpus and by two on seed 7, in every category but provenance. The text arm alone is
one to seven points behind the fusion: BM25 over short extracted sentences has fewer terms to work
with than BM25 over the notes they came from, and the corpus's three names for every service cost
it more than they cost the embedding. The graph arm alone answers 27% and 21%. That is less the
graph failing to answer than the graph rarely being asked: the arm expands from the entities the
question names, and the automatic seeding matched an entity for 86 of the 150 questions on the
committed corpus and 80 on seed 7; for the rest the arm returns nothing and the model refuses.
Where it did fire, the fusion used it. Both seed 7 wins are graph chains: the on-call engineer of
the team that owns search-indexer, and the complete list of six services Dune owns, which every
raw-note system truncated.

Reciprocal rank fusion gives each arm an equal vote, so a text arm that ranks the wrong memories
first costs the fusion questions the vector arm had right. A weighted fusion, or a text arm that
stands down when the vector arm is confident, is the obvious next experiment; it is not done
here.

downgraded in either build: when the model named the memory a note corrects, the pipeline found
it. The temporal row runs the other way on seed 7, the oracle at 92% against the model at 100%,
which is two questions and is noise.

### Where anatid lost, and where it won

Against the five budgeted baselines (S1, S2, S3, S2+S3 and S3 with feedback), a win is a question
S4 alone answered correctly and a loss is one S4 got wrong while at least one baseline got it
right. The full lists, with every answer, are in each run's `REPORT.md` and `summary.json`.

**Committed corpus.** anatid alone right on no question; wrong where at least one baseline was
right on 21. Thirteen of the 21 are refusals on facts the store does not hold in a findable form:
an approval rule, an incident date, a current owner, an owner and an on-call engineer at a past
date, a team before a move, three deploy windows two hops away, three chains through a dependency,
and the note behind a move. Three are stale values: the previous pager holder, the previous team,
an earlier on-call engineer. The other five are a handover dated to a later restatement, two chains
that landed on the wrong person, a list of a team's services with one missing, and a provenance
answer that named a later note than the first record. On fourteen of the 21, all four raw-note
retrievers were right.

**Seed 7.** anatid alone right on two questions, both multi-hop, both graph chains; wrong where a
baseline was right on eight. Six of the eight are refusals: five multi-hop chains through a
dependency and one decision reason the extractor did not record. One is a stale owner. One is a
provenance question answered with the date of a later restatement instead of the first record. On
six of the eight, all four raw-note retrievers were right.

### Cost and time

Building the anatid store is the one expensive step: about 600 model calls per world (one
extraction call per note, one embedding per memory written, one per context lookup), $0.14 and
$0.09 at the provider's price, and 54 and 69 minutes of model time when first made. The vector
index costs 178 embeddings, under one cent and under nine seconds; BM25 and the Markdown file cost
nothing. Answering costs about the same everywhere, one to five cents for 150 questions; anatid's
memory block is the shortest of the budgeted retrievers, about 1,100 tokens against 1,180, and its
answers cost two to three cents in both worlds, in the same range as the raw-note retrievers'.
Retrieval takes under ten seconds for all 150 questions on every system; the 56 seconds for vectors
with feedback on the committed corpus is the network time of the 150 feedback embeddings the first
time they were made.

A cold run of one world costs about half a dollar in model calls, of which the judge is six to
seven cents. The runs behind these tables charged $0.04 and $0.05, for the two fused baselines'
answers and their judging; everything else came from the cache. An offline replay charges nothing
and reports the same numbers.

## What to take from it

On this corpus, at this budget, with this model, an agent does not answer better from anatid
than from a vector index over the raw notes, and on one of the two worlds it answers clearly
worse. The gap is extraction, not retrieval: the same store built from perfect patches is the
best budgeted system in both worlds, and anatid's own vector arm over the model's memories is
level with the vector baseline. What anatid buys is visible where it wins, which is chains and
complete lists, and in the size of its context. What it costs is a model pass over every note, a
refusal rate two to four times the baselines', and stale edges the extractor did not close. The
next things to try are in the extractor and the fusion rather than the storage: close edges on
handovers, weight the arms, seed the graph arm from more than exact entity names. Until those are
done, these are the numbers.

## Reproduce

```
python -m bench.quality.run --run-id s20260905-b1200 --seed 20260905 --budget 1200 --counter chars4 --family builtin
python -m bench.quality.run --run-id s7-b1200 --seed 7 --budget 1200 --counter chars4 --family builtin
```

The first command runs on the committed corpus (`bench/quality/data/`); the second generates and
verifies the seed 7 corpus into its run directory first, deterministically. Each reads the key
from `OPEN_ROUTER_KEY` or `.env`, caches every model call under `bench/quality/cache/`, writes
every prompt, context and answer under `bench/quality/results/<run>/<system>/`, and renders
`bench/quality/results/REPORT.md` and a copy in the run directory. Add `--offline` to prove a rerun
needs no network: with a warm cache each finishes in about a minute with zero charged cost and
the same numbers. `--counter chars4` pins the token counter these runs used; with `tiktoken`
installed and `--counter auto`, the budget is counted differently, the prompts change and the
cache is cold. `--limit 10 --systems markdown,bm25` is a smoke run; `--family external` runs the
same systems through the `bench.quality.systems` package instead of the harness's built-ins.
