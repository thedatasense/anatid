# anatid Phase 0 spike: benchmark contract

Purpose: decide, with numbers, whether a DuckDB-based engine can serve agent-memory graph workloads
within 5x of LadybugDB (the maintained Kuzu fork) on the query that matters most: 2-hop recall.

Kill criterion (from the plan): if DuckDB 2-hop recall (R1) is more than 5x slower than LadybugDB
at the 1M-fact scale after a week of tuning, revisit the DuckDB-extension-first angle.
The spike reports the ratio at p50 and p95 for both DuckDB layers (SQL macros, C++ CSR table function).

Everything below is a contract. Every engine runner must implement the same dataset load, the same
operations with the same semantics, and write results in the same JSON shape so `report.py` can
compare them and check that the engines return the same answers.

## Layout

```
spike/
  SPEC.md                 this file
  bench/
    gen_dataset.py        deterministic synthetic dataset -> Parquet (seed 42)
    common.py             shared harness: dataset paths, workload schedule, timing, metrics, result JSON
    run_duckdb_sql.py     engine "duckdb_sql": DuckDB 1.5.5, tables + SQL macros (Layer A)
    run_duckdb_ext.py     engine "duckdb_ext": same tables, graph_expand from the C++ extension (Layer B)
    run_ladybug.py        engine "ladybug": LadybugDB 0.20.2, Cypher
    run_grafeo.py         engine "grafeo": Grafeo 0.5.x (optional; report "unsupported" per op if needed)
    report.py             merges results/*.json -> results/REPORT.md with the kill-criterion verdict
  duckdb_sql/
    schema.sql            node/edge tables with system columns
    macros.sql            graph_expand, recall_2hop, recall_hybrid, remember, supersede as macros
  extension/              DuckDB extension template pinned to duckdb v1.5.5 (name: anatid)
  data/<scale>/           generated Parquet (gitignored)
  results/                <engine>.<scale>.json, REPORT.md (checked in)
```

## Dataset

Generated by `gen_dataset.py --scale {small,full}` with numpy seed 42. `small` = 100k memories
(for development), `full` = 1M memories (the kill-criterion run). Counts below are for `full`;
`small` is everything divided by 10.

Ten tenants, `tenant_id` 0..9, every row belongs to exactly one tenant, edges never cross tenants.

| file | rows (full) | columns |
|---|---|---|
| `entities.parquet` | 100,000 (10k/tenant) | entity_id INT64 (global unique, dense 0..N-1), tenant_id INT32, kind VARCHAR (person/project/topic/tool/doc), name VARCHAR |
| `memories.parquet` | 1,000,000 | memory_id INT64 (dense 0..N-1), tenant_id INT32, content VARCHAR, kind VARCHAR (episodic/semantic/preference/procedural), embedding FLOAT[64] (L2-normalized), created_at TIMESTAMP, valid_from TIMESTAMP, valid_to TIMESTAMP (NULL = current; ~5% non-NULL), tx_from TIMESTAMP, tx_to TIMESTAMP (NULL), writer VARCHAR (agent id), episode_id INT64, confidence FLOAT |
| `edges_about.parquet` | ~2,000,000 | edge_id INT64, src INT64 (memory_id), dst INT64 (entity_id), tenant_id INT32, weight FLOAT, valid_from, valid_to, tx_from, tx_to |
| `edges_relates.parquet` | ~300,000 | edge_id INT64, src INT64 (entity_id), dst INT64 (entity_id), tenant_id INT32, rel_kind VARCHAR, valid_from, valid_to, tx_from, tx_to |
| `edges_supersedes.parquet` | 50,000 | edge_id INT64, src INT64 (newer memory_id), dst INT64 (older memory_id), tenant_id INT32, tx_from |
| `queries.parquet` | 2,000 | query_id INT32, tenant_id INT32, seed_entity_id INT64, query_text VARCHAR, query_embedding FLOAT[64] |
| `writes_memories.parquet` | 100,000 | same columns as memories (memory_id continues after 1M), plus about_dsts LIST<INT64> (1..3 entity ids, same tenant) |
| `writes_supersedes.parquet` | 10,000 | new memory_id (from writes_memories), old_memory_id (existing, same tenant) |

Signal, so that recall has something to find:
- Entities have a hidden 64-d centroid. A memory's embedding = mean of its ABOUT entities' centroids + N(0, 0.35) noise, normalized.
- Vocabulary ~5,000 words. Each entity owns 3 "topic words"; a memory's content is 12..30 words drawn 60% from its ABOUT entities' topic words and 40% from the global vocabulary.
- `query_text` = 2..4 topic words of the seed entity; `query_embedding` = seed centroid + small noise, normalized.
- RELATES_TO degree follows a Zipf-like distribution (avg 3, a few hubs with 200+), so 2-hop frontiers vary from ~5 to ~5,000 entities.
- Every ABOUT edge picks 1..3 entities from the memory's tenant, biased toward the memory's "home" entity's RELATES_TO neighbours (so 2-hop recall finds real clusters).

## Operations (identical semantics on every engine)

All timestamps are UTC. `now` is the harness clock passed in as a parameter, never the engine's clock,
so the engines produce identical results.

- **R1 `recall_2hop(tenant_id, seed_entity_id, limit=20)`** -- the kill-criterion query.
  Frontier F = seed plus all entities reachable from seed by 1 or 2 hops over RELATES_TO edges
  (either direction, edges with `valid_to IS NULL`, same tenant). Return memories m such that
  m ABOUT some e in F, `m.valid_to IS NULL`, `m.tenant_id = tenant_id`; order by `m.created_at DESC, m.memory_id DESC`;
  take `limit`. Return `(memory_id, created_at)`. Results must be identical across engines.
- **R2 `recall_hybrid(tenant_id, query_text, query_embedding, k=20)`**
  A = top 50 memories of the tenant by cosine similarity to `query_embedding` (current only).
  B = top 50 memories of the tenant by BM25 over `content` for `query_text` (current only).
  Fuse with RRF (k=60): score = sum over lists of 1/(60+rank). Return top `k` `(memory_id, rrf_score)`,
  each with the list of ABOUT entity names (1-hop context). Not part of the kill criterion; report it.
  Engines may use an ANN or FTS index; the report records which. If an engine cannot do BM25 (or FTS
  is not incremental after writes), record that in `notes` and report recall@20 vs brute-force truth.
- **W1 `remember(memory_row, about_dsts)`** -- one transaction: insert one memory (valid_from = tx_from = now,
  valid_to = tx_to = NULL) and its 1..3 ABOUT edges.
- **W2 `supersede(old_memory_id, new_memory_row)`** -- one transaction: insert the new memory, set
  `valid_to = now` on the old memory (do not delete), insert a SUPERSEDES edge new -> old.

## Workload schedule

Deterministic, produced by `common.schedule(scale, seed=7)` so every engine executes the same op list:

1. **load**: bulk-load all Parquet files; build whatever indexes the engine uses for R1/R2. Record wall time and DB size on disk.
2. **warmup**: 50 R1 queries (not timed).
3. **r1_only**: 1,000 R1 queries (query_ids 0..999) -- the kill-criterion measurement, single thread.
4. **r2_only**: 300 R2 queries (query_ids 1000..1299), single thread.
5. **mixed**: 10,000 ops, single thread, 70% writes / 30% reads: writes are 90% W1, 10% W2; reads are 80% R1, 20% R2. Ops drawn from the writes files and query_ids 1300..1999 (wrapping).
6. **concurrent** (optional but requested): 4 writer threads doing W1 plus 2 reader threads doing R1 for 30 seconds against the same open database, each thread with its own connection. Record total ops/s per type and error count (LadybugDB is documented single-writer per process; DuckDB is optimistic MVCC; note behaviour honestly, including retries).
7. **verify**: re-run R1 for query_ids 0..199 after the mixed phase and dump `(query_id, [memory_id...])` into the result JSON so `report.py` can check engines agree exactly (the same writes happened everywhere).

Timing: `time.perf_counter_ns()` around the whole op including result materialization to Python lists.
Latency percentiles in milliseconds. Peak RSS via `resource.getrusage`.

## report.py

Reads all `results/*.<scale>.json`, produces `results/REPORT.md` with:
- a table of R1/R2/W1/W2 p50/p95 and ops/s per engine,
- the kill-criterion line: `ratio_p50 = duckdb_x.R1.p50 / ladybug.R1.p50` (and p95) for each DuckDB layer, verdict PASS if <= 5 else FAIL,
- a verify section: number of query_ids where engines' R1 id lists differ (must be 0; otherwise the benchmark is invalid and the report says so),
- load time, DB size, peak RSS, and each engine's notes.

## Engine notes

- **duckdb_sql**: file-backed DB (`results/anatid.duckdb`, deleted before load). Tables per `schema.sql`.
  R1 as a SQL macro; try both a recursive CTE with `USING KEY` and a two-self-join formulation, keep the
  faster, record both in notes. Consider ART indexes on `(tenant_id, src)` / `(tenant_id, dst)` and on
  `memories(memory_id)`; measure with and without. R2 uses `array_cosine_similarity` brute force plus the
  `fts` extension (`PRAGMA create_fts_index`); the fts index is not incremental, so note staleness after writes.
- **duckdb_ext**: same load as duckdb_sql, but R1's frontier comes from `graph_expand(tenant_id, seed, 2)`,
  a C++ table function over an in-memory CSR built once after load from `edges_relates` (both directions),
  and refreshed by calling `anatid_build_csr()` again (the spike may rebuild at the start of each phase;
  record the rebuild cost). Load the unsigned extension with `allow_unsigned_extensions`.
- **ladybug**: file-backed DB (`results/anatid.lbdb`). `CREATE NODE TABLE Entity/Memory`, `CREATE REL TABLE
  ABOUT/RELATES_TO/SUPERSEDES` with the same columns; `COPY ... FROM parquet`. R1 in Cypher with
  `-[:RELATES_TO*0..2]-` (undirected) plus the filters above. `INSTALL FTS; LOAD FTS; INSTALL VECTOR; LOAD VECTOR;`
  then `CREATE_FTS_INDEX` and `CREATE_VECTOR_INDEX` for R2 (record whether the vector index is used).
- **grafeo**: best effort. If an op cannot be expressed, mark it `unsupported` and keep going.

## Rules

- Never compare numbers taken while another benchmark or a compiler build is running on the machine.
- Report failures as failures. A phase that errors is recorded with the error, not silently skipped.
- No engine-specific shortcuts that change semantics (for example dropping the tenant filter or the validity filter).
